### Pattern 1: Categorical + observed=True
**What:** Convert high-cardinality string columns to pd.Categorical at read time, then add `observed=True` to all groupby calls.
**When to use:** Every groupby on Categorical columns. Without `observed=True`, pandas generates the Cartesian product of all category levels (potentially millions of empty groups).
**Example:**
```python
# P2: In parquet_store.py or readers.py
CATEGORICAL_COLUMNS = {
    "race_id", "kettonum", "kisyucode", "chokyosicode",
    "sire_id", "bms_id", "umaban",
}

def _optimize_dtypes(df: pd.DataFrame) -> pd.DataFrame:
    for col in CATEGORICAL_COLUMNS & set(df.columns):
        if df[col].dtype == object:
            df[col] = df[col].astype("category")
    return df

# Every groupby call site:
# Before:
df.groupby(["race_id", "kisyucode"])
# After:
df.groupby(["race_id", "kisyucode"], observed=True)
```
Source: Spike 004 validated 1.3-3.3x speedup for all operations + 92.6% memory reduction [VERIFIED: .planning/spikes/004-gpu-cpu-memory/README.md]

### Pattern 2: MLflow pip_requirements bypass
**What:** Pass explicit `pip_requirements` list to `mlflow.lightgbm.log_model()` to skip the `pip freeze` subprocess.
**When to use:** Every `mlflow.lightgbm.log_model()` call (16 calls in _log_to_mlflow).
**Example:**
```python
_PIP_REQS = ["lightgbm", "scikit-learn", "pandas", "numpy", "joblib"]
mlflow.lightgbm.log_model(model, name="model_name", pip_requirements=_PIP_REQS)
```
Source: Spike 005 validated 57.6x speedup per call (4.377s -> 0.076s) [VERIFIED: .planning/spikes/005-p1-quick-wins/README.md]

### Anti-Patterns to Avoid
- **observed=False (default) with Categorical columns:** 70x slowdown on multi-column groupby. Spike 004 confirmed this with real measurement. [VERIFIED: .planning/spikes/004-gpu-cpu-memory/README.md]
- **GPU training for keiba-ai data sizes:** GPU transfer overhead dominates for 50k-200k row datasets. Spike 004 confirmed 1.5-5.5x SLOWER. [VERIFIED: .planning/spikes/004-gpu-cpu-memory/README.md]
- **ThreadPoolExecutor max_workers > 2:** Oversubscription with LightGBM's internal OpenMP threads. Spike 004 confirmed 2 is optimal. [VERIFIED: .planning/spikes/004-gpu-cpu-memory/README.md]
- **Incomplete observed=True coverage:** Missing even one multi-column groupby on Categorical columns can cause catastrophic regression.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| pip requirements inference | Custom subprocess caching | `pip_requirements=["lightgbm", ...]` parameter | MLflow already supports this; just pass the list [CITED: mlflow.org/docs/latest/python_api/mlflow.lightgbm.html] |
| String column performance | Custom hash tables | `pd.Categorical` dtype | pandas uses integer-based hashing internally for Categorical [CITED: pandas docs] |
| Odds data caching | Complex LRU with eviction | Pass DataFrames between phases | Backtest pipeline phases run sequentially; pass pre-loaded data as constructor args |
| Memory management | Manual GC tuning | Categorical dtype (92% memory reduction) | Reduces GC pressure automatically [VERIFIED: Spike 004] |

**Key insight:** The optimizations are mostly configuration changes and dtype conversions, not algorithmic rewrites (except P3 vectorization). This minimizes risk.

## Common Pitfalls

### Pitfall 1: Categorical merge incompatibility
**What goes wrong:** Two DataFrames with Categorical columns that have different category sets produce unexpected NaN on merge.
**Why it happens:** pandas Categorical merge uses integer codes; mismatched categories cause codes to not align.
**How to avoid:** Use `df[col].cat.set_categories()` to unify categories before merge, or convert to `str` at merge boundaries. The safest approach: convert at ParquetStore read time so all DataFrames in the same process share the same category pool.
**Warning signs:** NaN values appearing in columns that previously had no NaN.

### Pitfall 2: observed=True forgotten on new groupby calls
**What goes wrong:** A single groupby call without `observed=True` on Categorical columns can cause 70x regression.
**Why it happens:** pandas default is `observed=False` (before 3.0), which computes the Cartesian product of all category levels.
**How to avoid:** Systematic grep for all `.groupby(` calls in `src/`. Add `observed=True` to every one. Use code review checklist.
**Warning signs:** Sudden massive slowdown after Categorical conversion; groupby operations taking seconds instead of milliseconds.

### Pitfall 3: Calibration BT silently produces different results after changes
**What goes wrong:** After P0 skip, running with `--strategy-manifest` could produce different calibration results than before.
**Why it happens:** Optuna-optimized `roi_threshold` may be different from default 1.0, making calibration meaningful.
**How to avoid:** D-02 mandates calibration only with `--strategy-manifest`. Test both paths: default (skip) and manifest (run lightweight calibration).
**Warning signs:** ROI or bet_count differing by more than 5% when running with `--strategy-manifest`.

### Pitfall 4: P3 vectorization float precision drift
**What goes wrong:** Replacing itertuples with vectorized groupby+rolling produces slightly different floating-point results.
**Why it happens:** Different order of floating-point operations (sequential vs. batch).
**How to avoid:** D-06 allows statistical tolerance (< 5% ROI/bet_count, < 1% hit rate). Implement comparison test.
**Warning signs:** Exact match test failing on P3 changes (expected for floating-point reasons).

### Pitfall 5: Test fixture incompatibility with Categorical dtype
**What goes wrong:** Existing mock-based tests create DataFrames with object/string dtype, which behave differently from Categorical in merge/groupby operations.
**Why it happens:** Tests use `pd.DataFrame({"race_id": ["202401010101"], ...})` which creates object columns, not Categorical.
**How to avoid:** Either (a) add Categorical conversion in test fixtures, or (b) ensure _optimize_dtypes is applied in test data setup. Since tests mock ParquetStore, the Categorical conversion happens at read time and may not propagate to mock data.
**Warning signs:** Tests failing with `TypeError: Cannot merge Categorical with object` or similar.

## Open Questions (RESOLVED)

1. **P3 vectorization scope (RESOLVED)** — Full vectorization of the itertuples loop in horse_history_features.py:592 is deferred. The loop computes ~20 features per horse with complex logic (form cycle, class adjustment, hierarchical z-score) that does not cleanly map to groupby+rolling.
   - **Resolution:** Implement class-level cache (_class_cache) for cross-instance data sharing (~100s savings) + per-race add_race_transforms dedup (~50-100s savings). Phase goal (50% reduction) is met by P0 alone (-4900s, -60%). P3 cache+dedup provides additional margin.
   - **Rationale:** MEDIUM confidence in full vectorization feasibility (assumption A3). Cache enhancement is LOW risk, HIGH value. Per-race dedup is mathematically equivalent (single-race DataFrame rank == groupby("race_id").rank when only one group exists).

2. **Categorical merge safety (RESOLVED)** — When two DataFrames with different Categorical category sets are merged, pandas may produce unexpected NaN.
   - **Resolution:** Apply Categorical at ParquetStore.read() time (D-04). Within a single read() call, all rows share the same category pool. Cross-load merges (different time ranges) will have different category sets, but pandas handles this via `union_categoricals` internally when merging. If issues arise, `.astype(str)` at merge boundaries is a safe fallback.
   - **Rationale:** _optimize_dtypes applies on every read(), ensuring consistency within each load. Cross-load merges are rare in the pipeline (most operations use a single time range). Tests will catch regressions.

3. **Pass-through vs LRU cache for odds data (RESOLVED)** — Two approaches for avoiding 3x reload of odds_ts data.
   - **Resolution:** Pass-through via constructor injection (preloaded_odds_ts parameter on BacktestEngine). This aligns with the existing "constructor injection" pattern used throughout the codebase and is more testable than LRU cache.
   - **Rationale:** Plan 02 implements preloaded_odds_ts on BacktestEngine.__init__(). Test mocking is straightforward (pass DataFrame or None). LRU cache would require cache invalidation logic and is less transparent.
