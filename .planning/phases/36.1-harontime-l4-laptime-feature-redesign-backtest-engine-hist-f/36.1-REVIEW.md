## Summary

Reviewed 16 files from Phase 36.1 (HaronTime L4/LapTime feature redesign + backtest engine hist f). The changes introduce new features (closing_speed_ratio, haron_race_gap, pace_adj_finish, pace_ratio) with expanding-window z-scores, EMA weighting, and hierarchical fallback levels for PIT-safe computation. All 12 model FEATURE_COLS lists were updated to include the new Phase 36.1 features.

One critical bug was found: the `_race_only_cols` filter in `horse_history_features.py` (line 476) always produces `["race_date", "harontimel4"]` because neither string equals `"race_id"`, meaning the filter condition is dead code and does not behave as its name implies. The merge still works by accident because `entries_filtered` may not contain those columns, but the intent is clearly wrong.

Seven warnings include: class-level mutable cache without bounds, in-place DataFrame mutation in conformal_ev_model, potential index misalignment in race_predictor.py place column transfer, duplicated `_safe_feature_cols` helper across 4 files, and a potentially infinite growing cache key in HorseHistoryFeatures.

Note: `tests/test_backtest_engine.py` exceeded the read limit and could not be fully reviewed. Findings below are based on the 15 successfully read files.

## Critical Issues

### CR-01: Dead-code filter condition produces unintended column list

**File:** `src/features/horse_history_features.py:476`
**Issue:** The list comprehension `[c for c in ["race_date", "harontimel4"] if c != "race_id"]` always evaluates to `["race_date", "harontimel4"]` because neither `"race_date"` nor `"harontimel4"` equals `"race_id"`. The filter condition `c != "race_id"` is dead code. The comment says "Drop columns that come from races_hist to avoid merge suffix conflicts" but the actual intent was likely to exclude `"race_id"` from the drop list so it remains available as a merge key. The current code always drops both `race_date` and `harontimel4` from `entries_filtered` regardless. While this may not cause a visible failure (because `entries_filtered` may not contain `harontimel4`), it means `race_date` is always dropped from entries even when that might not be desired, and the filter logic is incorrect.
**Fix:**
```python
# Line 476: The filter was meant to keep race_id and drop everything else
_race_only_cols = [c for c in ["race_date", "harontimel4"] if c in entries_filtered.columns]
```

## Warnings

### WR-01: Class-level mutable cache grows without bounds

**File:** `src/features/horse_history_features.py:280`
**Issue:** `HorseHistoryFeatures._class_cache` is a class-level `dict` that accumulates entries keyed by `f"{id(past_by_ketto_arr)}_{ketto}"` (line 397). For a training pipeline processing thousands of horses across multiple submodel invocations, this cache grows without any eviction or size limit. Memory usage depends on the number of unique `ketto` (blood registration) numbers. While `clear_class_cache()` exists, it is only called explicitly in tests. In production (e.g., full training pipeline), stale entries from previous submodel invocations may consume significant memory.
**Fix:** Add an LRU eviction strategy or clear the cache between submodel invocations at the call site.

### WR-02: In-place DataFrame mutation via column assignment in conformal_ev_model

**File:** `src/models/conformal_ev_model.py:461-462`
**Issue:** When feature columns are missing, the code assigns `win_df[c] = 0.0` directly. While `win_df` was created via `win_df.copy()` at line 408, the missing-column fill modifies the caller's conceptual copy. This is fragile because a future refactoring that removes the `.copy()` (e.g., for performance) would silently introduce a mutation bug. The pattern also masks potential training/serving skew where features present during training are silently zeroed during prediction.
**Fix:** Use explicit column filling on a fresh copy:
```python
missing_df = pd.DataFrame(0.0, index=win_df.index, columns=missing)
win_df = pd.concat([win_df, missing_df], axis=1)
```

### WR-03: Potential index misalignment in race_predictor place column transfer

**File:** `src/backtest/race_predictor.py:213-215`
**Issue:** After `predict_interval` returns `(win_df, place_df)`, the code does `df = win_df` then `df["EV_lower_place"] = place_df["EV_lower_place"].reindex(df.index).values`. If `win_df` and `place_df` have different index orderings (possible when they derive from different code paths inside `predict_interval`), `.reindex(df.index).values` silently reorders but the `.values` assignment bypasses pandas alignment checks. In the fallback path (lines 203-212), both `win_df` and `place_df` are copies of `df` so alignment is guaranteed, but in the conformal path (line 200), `predict_interval` does its own copies and transformations that could diverge.
**Fix:** Use pandas alignment instead of raw `.values`:
```python
df["EV_lower_place"] = place_df["EV_lower_place"].reindex(df.index)
```

### WR-04: Duplicated `_safe_feature_cols` helper across 4 model files

**File:** `src/models/market_model.py:15-27`, `src/models/regime_detector.py:18-26`, `src/models/race_quality_screener.py:15-23`, `src/models/wide_two_stage_model.py:18-26`
**Issue:** The `_safe_feature_cols` function is copy-pasted across 4 files with minor variations. `race_quality_screener.py` omits `.copy()` on the return (`return df[cols]` vs `return df[cols].copy()` in others). This means the screener returns a view that could trigger `SettingWithCopyWarning` if modified downstream, while the other three return safe copies.
**Fix:** Extract to a shared utility module (e.g., `src/models/utils.py`) and import consistently. Ensure all variants return `.copy()`.

### WR-05: Class cache key includes `id()` which is non-deterministic across runs

**File:** `src/features/horse_history_features.py:397`
**Issue:** `cache_key = f"{id(past_by_ketto_arr)}_{ketto}"` uses Python's `id()` which returns the memory address of the `past_by_ketto_arr` dict. This means cache keys are non-deterministic across runs, making the cache impossible to persist or debug. More critically, if `past_by_ketto_arr` is garbage-collected and a new dict is allocated at the same address, the cache could theoretically serve stale data for a different dict. In practice this is unlikely because the dict is held by the same instance, but it violates the principle of least surprise.
**Fix:** Use a deterministic cache key based on a hash of the dict contents or a stable identifier passed from the caller.

### WR-06: `_compute_haron_stats` returns NaN z-score placeholder, relies on separate code path

**File:** `src/features/horse_history_features.py:262-266`
**Issue:** `_compute_haron_stats` explicitly returns `"harontimel5_zscore": float("nan")` with a comment "compute()内で計算". This creates a split-brain pattern where the function's return value is partially computed (avg and trend are real values) but z-score is a placeholder NaN. If any caller uses the function's return directly without the separate expanding-stats computation, they get a silently wrong NaN. The function's docstring does not mention this contract.
**Fix:** Either compute z-score within the function or rename the key to `harontimel5_zscore_placeholder` and document the contract in the docstring.

### WR-07: EMA weight computation uses `(1 - decay)` base which differs from standard EMA

**File:** `src/features/horse_history_features.py:1097`
**Issue:** `weights_csr = (1 - decay_csr) ** np.arange(n_csr)` where `decay_csr = np.log(2) / halflife_csr`. The standard EMA weight formula is `alpha * (1 - alpha) ** t` where `alpha = 1 - exp(-ln(2)/halflife)`. The code uses `(1 - decay)` as the base, where `decay = ln(2)/halflife ~ 0.231`. This gives `(0.769) ** t` weighting. The standard formula would use `(1 - alpha) ** t` where `alpha = 1 - 0.5^(1/halflife) ~ 0.206`, giving `(0.794) ** t`. The difference is small but the implementation does not match the documented "halflife=3" convention used by pandas.
**Fix:** Use the standard EMA formulation: `alpha = 1 - np.exp(-np.log(2) / halflife)` and weight base `(1 - alpha)`.
