# Phase 36.1.1: MarketModel & RaceQuality配線修正 - Research

**Researched:** 2026-05-20
**Domain:** Feature routing / model contract enforcement / EV tail calibration
**Confidence:** HIGH

## Summary

Phase 36/36.1 added 28 fundamental horse-level features (TRF=3 race-rank, INT=3 interaction, HLF=20 haron/lap derived) to ALL model FEATURE_COLS lists uniformly. This was a design-level error: the MarketModel, RaceQualityScreener, and RegimeDetector all have specific contracts that should NOT include fundamental horse-ability features. The result is three cascading failures: (1) MarketModel's market-distortion signal is dominated by fundamental features (gain share 80%+), destroying its purpose as a residual-capture model; (2) RaceQualityScreener receives horse-level features but `build_race_features()` only constructs race-level aggregates, so all Phase36 columns are NaN during inference -- the screener's model trains with NaN-filled features, producing degenerate scores that exclude 71.9% of profitable races; (3) RegimeDetector receives fundamental features that have no business being in a market-state classifier. Additionally, `quality_score` is hardcoded to `0.0` in the BacktestEngine diagnostic logger (lines 998 and 1089), meaning even if the screener produced meaningful scores, they are never logged.

**Primary recommendation:** Remove Phase36 fundamental features from MarketModel, RaceQualityScreener, and RegimeDetector FEATURE_COLS. For RaceQualityScreener, add race-aggregate Phase36 features (top1_strength, top1_top2_gap, form_signal_dispersion) computed from horse-level Phase36 values. Implement EV tail calibration for high-EV longshots using feature family agreement scoring. Fix quality_score logging in BacktestEngine.

### Pattern 1: Model-Specific Feature Routing
**What:** Each model has its own FEATURE_COLS that reflects its architectural role
**When to use:** Always -- never blanket-add features across all models
**Example:**
```python
# MarketModel: market-only features (NO fundamental horse features)
FEATURE_COLS: list[str] = [
    "surface", "distance_bin", "track_condition_code",  # race conditions
    "implied_prob_hhi", "odds_skewness",                 # market structure
    "rl_log_odds_entropy", "rl_odds_dispersion",         # race-level market
    # NEVER: form_trend_race_rank, closing_speed_ratio_avg, etc.
]
```

### Pattern 2: Race-Level Aggregation for Screener
**What:** Horse-level features aggregated to race-level for RaceQualityScreener
**When to use:** When a race-level model needs information derived from horse-level features
**Example:**
```python
# In _build_race_level_features() or build_race_features():
race_feat["phase36_top1_strength"] = (
    feat_df.groupby("race_id")["closing_speed_ratio_avg"].max()
)
race_feat["phase36_top1_top2_gap"] = (
    feat_df.groupby("race_id")["closing_speed_ratio_avg"]
    .apply(lambda x: x.nlargest(2).diff().iloc[-1] if len(x) >= 2 else 0.0)
)
```

### Anti-Patterns to Avoid
- **Uniform FEATURE_COLS across all models:** Never add features to all models without considering each model's architectural role. MarketModel MUST remain market-only; RaceQualityScreener MUST remain race-level-only.
- **Horse-level features in race-level models:** Horse-level features (form_trend, closing_speed_ratio) in RaceQualityScreener will be NaN during inference because `build_race_features()` aggregates to dict with only race-level keys.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Race-level aggregation | Custom aggregation per feature | pandas groupby().agg() with named agg | Standard pattern, already used in _build_race_level_features() |
| Feature family agreement | Complex Bayesian agreement model | Simple majority vote across feature families (TRF, INT, HLF, market, ability) | Keeps complexity low; this is Phase 36.1.1 triage, not research |

**Key insight:** The fix is surgical removal and targeted addition, not new infrastructure.

## Common Pitfalls

### Pitfall 1: Removing Phase36 from models that benefit
**What goes wrong:** Removing Phase36 from ALL models including AbilityModel, WinTwoStageModel
**Why it happens:** Overcorrecting the uniform-add by uniform-removing
**How to avoid:** Only remove from MarketModel, RaceQualityScreener, RegimeDetector. Keep in AbilityModel, WinTwoStageModel, PlaceTwoStageModel, PlaceAbilityModel, EVCorrectionModel, ConformalEVModel, WideTwoStageModel.
**Warning signs:** If BT ROI drops further after fix, check that fundamental models still have their features.

### Pitfall 2: build_race_features() missing new aggregate columns
**What goes wrong:** Adding new FEATURE_COLS to RaceQualityScreener but not updating build_race_features() to construct them
**Why it happens:** build_race_features() is in race_predictor.py, not in race_quality_screener.py
**How to avoid:** Any new column added to RaceQualityScreener.FEATURE_COLS must also appear in either: (1) build_race_features() in race_predictor.py, OR (2) _build_race_level_features() in training_pipeline.py
**Warning signs:** NaN in RaceQualityScreener feature values during backtest

### Pitfall 3: quality_score still hardcoded to 0.0 after fix
**What goes wrong:** Fixing the screener model but forgetting to update BacktestEngine diagnostic logging
**Why it happens:** quality_score appears in two places: engine.py line 998 (quality_passed=False) and line 1089 (quality_passed=True)
**How to avoid:** After fixing screener, extract the actual predicted quality_score and pass it to diag_logger.log_race()
**Warning signs:** Diagnostic CSV shows all quality_score=0.0

### Pitfall 4: EV tail calibration treating all high-EV the same
**What goes wrong:** Applying a blanket EV cap or scale to all EV>=1.5 bets
**Why it happens:** Simpler implementation
**How to avoid:** Use feature family agreement -- Phase36 single-family bounce (only one family signals strength) should be shrunk; multi-family agreement (2+ families agree) should be treated aggressively
**Warning signs:** High-EV longshot win rate drops to zero

### Pitfall 5: Breaking existing tests
**What goes wrong:** Tests that construct fixture data with specific FEATURE_COLS lengths fail after removal
**Why it happens:** Tests hardcode or check FEATURE_COLS membership
**How to avoid:** Run full test suite after each FEATURE_COLS modification; update fixture data to match
**Warning signs:** pytest failures in test_market_model.py, test_race_quality_screener.py

## Feature Family Agreement for EV Tail Calibration (RTG-04)

### Feature Families:
| Family | Features | Signal |
|--------|----------|--------|
| TRF (race-rank) | form_trend_race_rank, blood_total_wr_race_rank, blood_surface_wr_race_rank | Relative form strength |
| INT (interaction) | grade_x_form_trend, distance_x_closing_index, grade_x_blood_prize_log | Context-adjusted ability |
| HLF (haron/lap) | closing_speed_ratio_avg, harontime_last3f_avg, haron_race_gap_avg, pace_ratio_avg | Physical ability |
| Market | implied_prob_hhi, odds_skewness, overround, market_entropy | Market undervaluation |
| Ability (Stage1) | p_ability_win, p_ability_place | Model confidence |

### Agreement Logic:
```python
# For EV >= 1.5 candidates:
# 1. Compute per-family z-score relative to race mean
# 2. Count families with z > 1.0 (positive signal)
# 3. Single-family bounce (count=1): shrink EV by 0.85x
# 4. Multi-family agreement (count>=2): keep EV or boost by 1.05x
# 5. No family agreement (count=0): shrink EV by 0.70x
```

## Open Questions

1. **Should EVCorrectionModel keep Phase36 features?**
   - What we know: EVCorrectionModel is a Stage2 correction model that uses both market and ability features
   - What's unclear: Whether Phase36 fundamental features improve EV correction or just add noise
   - Recommendation: KEEP for now; evaluate with gain importance after BT retrain. The EVCorrectionModel legitimately uses both p_win and market signals, so fundamental features that inform p_win could be useful.

2. **What is the exact quality_score propagation path?**
   - What we know: RaceQualityScreener.should_bet() returns bool but internally computes a score
   - What's unclear: Whether to add a new method like `get_quality_score()` or modify `should_bet()` return type
   - Recommendation: Add a separate `predict_score()` method that returns float, and modify `should_bet()` to call it internally. This avoids breaking the Protocol interface.

3. **How many race-aggregate Phase36 features are needed?**
   - What we know: 5 proposed aggregates (top1_strength, top1_top2_gap, field_dispersion, form_signal_dispersion, weighted_form_mean)
   - What's unclear: Whether this is too few (screener under-informed) or too many (overfit risk)
   - Recommendation: Start with 5, evaluate screener independence test (<0.30 correlation with edge_max_per_race)
