# Phase 36.1.1.1: roi-diagnostic-fixes-and-feature-sanity-optimization - Context

**Gathered:** 2026-05-21
**Status:** Ready for planning
**Source:** User delegated technical choices to best-practice judgment: "実装難易度は問わないのでベストプラクティスを追求してくれ。"

<domain>
## Phase Boundary

This phase converts the findings from `ROI_ANALYSIS_REPORT_20260521.md` and
`ANALYSIS-bt2024-features.md` into reliable implementation work before Phase 37
EV calibration. It must make the backtest diagnostic artifacts internally
consistent, stop high-EV/high-odds tail blowups from contaminating ROI, replace
the fake OOF artifact with true time-series OOF outputs, fix or exclude unhealthy
features, and record feature timing so "前日" and "発走前" evaluation modes cannot
be mixed.

The phase is diagnostic and safety infrastructure for win-model ROI work. It is
not a new model architecture phase, not a new data-source phase, and not a Phase
37 calibration implementation phase.

</domain>

<decisions>
## Implementation Decisions

### User Delegation
- **D-00:** The user selected all five gray areas and delegated technical choices to
  best-practice judgment. Downstream agents should not re-ask threshold/source-of-truth
  questions unless implementation discovers a contradiction in the local data.
- **D-00b:** Optimization must favor diagnostic reliability, leakage resistance, and
  reproducibility over short-term ease or minimal code churn.

### 実ベット診断の正本化
- **D-01:** `stake` is the canonical source of truth for actual bets. Define
  `is_actual_bet = stake.notna() & (stake > 0)` and use it for all ROI, hit-rate,
  and candidate/selection diagnostics. Existing `is_bet` may remain only as a
  deprecated compatibility field or mirror, and any mismatch with `is_actual_bet`
  must fail validation.
- **D-02:** Every run must have a stable `backtest_run_id` and `generated_at_utc`
  written into all related artifacts. Include at least: git commit, train/test
  dates, test year, betting target, strategy manifest hash when present, feature
  manifest hash when present, and model directory.
- **D-03:** `bt_2024_horse_diagnostics.csv`,
  `bt_2024_horse_features.parquet`, `predictions/2024.parquet`,
  `multi_year_bet_history.json`, and validation reports must be generated from
  the same run. If metadata does not match, the diagnostic validator must fail
  rather than allowing stale cross-run merges.
- **D-04:** `BacktestEngine` / `DiagnosticLogger` should save selection diagnostics
  for win bets as first-class fields, not only place-oriented fields. Required
  fields include `selection_reason`, `excluded_reason`, `filter_pass_flags`,
  candidate counts before/after each filter, ranks by `p_win_final` and
  `win_selection_ev`, `p_win_pred`, `p_win_corrected`, `p_win_final`,
  `e_return_win_pred`, `e_return_win_corrected`, `win_selection_ev`,
  `win_selection_edge`, `win_gate_score`, `win_gate_pass`, `pre_odds`,
  `final_odds`, `odds_source`, `regime`, `quality_score`, `quality_passed`,
  `stake`, and `result`.
- **D-05:** Artifact validation must assert
  `is_actual_bet == (stake.notna() & (stake > 0))` for
  `predictions/{year}.parquet`, no non-null zero-stake rows are counted as bets,
  no duplicate actual bets exist for the same `race_id + umaban + bet_type`, and
  one consistent metadata block exists across all artifacts in the run.

### 高EV・高オッズ尾部の防御ルール
- **D-06:** Add a configurable win-tail risk filter after candidate generation and
  before stake sizing. It must operate only on prediction-time-safe fields such as
  decision-time odds, `win_selection_ev`, `p_win_final`, `win_gate_rank`, and
  feature-family agreement already available at prediction time.
- **D-07:** Default defensive policy for planning:
  - block `odds >= 100`
  - block `win_selection_ev >= 5`
  - for `50 <= odds < 100`, require strong probability/rank evidence
    (`p_win_final` rank near the top of the race, preferably `<= 3`) and shrink
    stake if allowed
  - for `3 <= win_selection_ev < 5`, shrink stake unless probability/rank gates
    pass
  These thresholds are intentionally conservative because the latest report shows
  `ev>=5` had 50 bets, 0 wins, ROI 0.00%.
- **D-08:** Tail rules must be pre-registered in configuration or strategy manifest
  before validation. Do not tune them on the same 2024 result file that reported
  the failure. Verification should compare baseline vs tail-filtered behavior via
  walk-forward or at minimum replay with clearly labeled "diagnostic only" output.
- **D-09:** Every tail exclusion or shrink must emit a machine-readable
  `excluded_reason` or `stake_multiplier_reason`, so future ROI reports can
  distinguish model prediction failure from risk-policy intervention.
- **D-10:** Do not introduce month-specific, race-name-specific, or hindsight
  segment filters in this phase. The report's February/July/monthly findings are
  diagnostic only and are too overfit for implementation.

### 真のOOF成果物
- **D-11:** Replace the current `data/oof/oof_predictions.parquet` write path that
  simply saves `full_features_df`. A valid OOF artifact must contain predictions
  generated by models that did not train on each row.
- **D-12:** The OOF artifact must include `fold_id`, `is_oof`, `train_start`,
  `train_end`, `valid_start`, `valid_end`, `model_version` or model hash,
  `feature_manifest_hash`, and the prediction columns used by IC/EV calibration
  (`p_ability_win_oof`, win probability outputs, EV outputs where available,
  labels, odds, race metadata).
- **D-13:** OOF folds must be time-series expanding or walk-forward folds. Random
  KFold is not acceptable for this artifact because downstream EV calibration and
  ROI diagnostics are time-dependent.
- **D-14:** Phase 37 must fail fast if a true OOF artifact is missing, has no
  `fold_id`, has `is_oof` missing/false for metric rows, or is byte/content-equal
  to `data/features/horse_features.parquet`.
- **D-15:** Metrics and calibration must filter to true OOF rows. If prefix rows
  cannot receive OOF predictions because they are used only for initial training,
  either exclude them from `oof_predictions.parquet` or mark them `is_oof=false`
  in a separate training-frame artifact. Do not mix non-OOF rows into OOF metrics.

### 特徴量健全化の優先順位
- **D-16:** Fix `sire_distance_wr` at the source. It is a win-rate feature and must
  be in `[0, 1]` or NaN. Add invariant checks for all rate-like blood/sire
  features; do not silently train on values such as 118.27. Root-cause fix is
  required, with clipping only as a final defensive guard that emits an audit
  warning.
- **D-17:** Fix `weight_change_zone` and `weight_change_ratio` to support both
  observed column spellings (`zogen_sa` and legacy/current `zogensa`) before
  declaring them usable. Keep NaN only when body-weight information is genuinely
  unavailable.
- **D-18:** `deviation_rank` and `deviation_zscore` may stay in model
  `FEATURE_COLS` only if they are computed and persisted consistently in both
  training and backtest/inference feature paths. If that cannot be completed in
  this phase, remove them from `FEATURE_COLS` until reliable.
- **D-19:** Audit `actual_pace_fit` and `kyakusitukubun_cd` together. Keep
  `actual_pace_fit` only if the code proves it uses prior-race
  `kyakusitukubun_cd` from `HorseHistoryFeatures`, never current-race
  `kyakusitukubun`. Add tests/manifest metadata to enforce that distinction.
- **D-20:** Add a feature availability and distribution validator comparing train
  vs backtest/inference frames. Critical failures include: feature trained with
  non-missing values but 100% NaN at backtest, rate columns outside valid bounds,
  constant columns in `FEATURE_COLS`, and incompatible timing-mode columns.
- **D-21:** Natural NaNs should remain NaN for LightGBM when missingness carries
  information. Add explicit missing flags only for high-value, semantically clear
  cases such as first-start/rest/body-weight history after validation.

### 予測時点 Manifest の線引き
- **D-22:** Add feature timing classification to the feature/model manifest. At
  minimum support: `pre_entry`, `previous_race_history`, `decision_time_odds`,
  `odds_timeseries_pre_race`, `derived_from_prediction`, `post_race_label`, and
  `forbidden_current_race_post`.
- **D-23:** The current model using final odds/popularity, wide odds, and odds
  dynamics must be labeled as a 発走前/投票締切直前 model, not a 前日 model.
- **D-24:** A 前日 model must exclude final `odds`/`tanodds`/`tanninki`,
  `fukuoddslow`, `wide_odds_*`, odds dynamics, odds deviation features derived
  from final odds, and market-cross features that require final market data.
- **D-25:** `kyakusitukubun_cd` is allowed only when sourced from past races.
  Current-race `kyakusitukubun` remains POST_RACE and forbidden. The manifest
  must distinguish these names and sources explicitly.
- **D-26:** Model training, backtest, paper trading, OOF, and Phase 37 calibration
  must all declare the same timing mode. Mixing 前日 and 発走前 features in one
  evaluation invalidates the run and should fail validation.

### Diagnostic Outputs
- **D-27:** Save EV decile, odds band, popularity band, and tail-segment ROI/hit
  diagnostics for every run. Include stake, return, hit count, bet count, and
  monotonicity summary for EV deciles.
- **D-28:** Diagnostic outputs are not optimization authority by themselves.
  Any rule learned from them must be validated with time-split or walk-forward
  evaluation before being treated as strategy improvement.

### the agent's Discretion
- Exact schema names for the run metadata block, as long as the required fields
  above are present and easy to validate.
- Exact class/function factoring for `DiagnosticLogger` vs `BacktestEngine`.
- Exact initial tail shrink multipliers for `50 <= odds < 100` and
  `3 <= win_selection_ev < 5`, provided defaults are conservative and
  configuration-driven.
- Whether true OOF is implemented by extending existing `TrainingPipelineV5`
  methods or by extracting a dedicated OOF writer/helper.
- Whether feature timing manifest is a new JSON artifact or an extension of the
  existing feature freeze manifest, provided it is hashed and attached to model
  and backtest outputs.

<code_context>
## Existing Code Insights

### Reusable Assets
- `BacktestEngine` already centralizes candidate generation, filtering, settlement,
  and diagnostic logging. It is the right integration point for `is_actual_bet`,
  run metadata, tail-risk filtering, and same-run artifact generation.
- `DiagnosticLogger` already writes race diagnostics, horse diagnostics, and horse
  feature parquet. Extend this instead of creating an unrelated logger.
- `WinSelectionGateModel.ensure_win_selection_columns()` already standardizes
  `win_selection_ev`, `win_selection_edge`, and `win_selection_prob`. Tail gates
  should reuse these columns.
- `OddsBandFilter` provides a simple existing pattern for candidate-level filtering
  and exclusion accounting.
- `TrainingPipelineV5.generate_ev_oof_predictions()` and model-specific OOF helpers
  provide starting points for true OOF artifact generation.
- Existing tests are mock-based and DB-free, so all new validation should be
  testable with synthetic DataFrames.

### Established Patterns
- Parquet files are the source of truth after ETL; PostgreSQL is ETL-only.
- POST_RACE safety is enforced through `POST_RACE_COLS` and model `FEATURE_COLS`.
- Current code often filters `FEATURE_COLS` to available columns, which can hide
  train/inference skew. This phase should add explicit validation for critical
  feature absence.
- LightGBM can handle natural NaNs, but 100% NaN in inference for a trained feature
  is a pipeline failure, not a model feature.
- Prior phases favor manifest/hash-based reproducibility; reuse that pattern for
  feature timing and run metadata.

### Integration Points
- `scripts/run_backtest.py::save_year_parquet()` currently merges diagnostics and
  bet history into `predictions/{year}.parquet`; this is a key place to enforce
  `is_actual_bet` and run metadata consistency.
- `src/backtest/engine.py` candidate-filter block is the natural location for the
  win-tail risk filter and exclusion accounting.
- `src/backtest/diagnostic_logger.py` schema needs to become win-aware and
  reason/flag-aware.
- `src/pipelines/training_pipeline.py` currently writes fake OOF by saving
  `full_features_df`; this must be replaced or guarded.
- `src/features/sire_features.py`, `src/features/feature_engine.py`, and
  `src/features/odds_deviation_features.py` are the first feature sanity targets.

</code_context>

<specifics>
## Specific Ideas

### Recommended Initial Tail Policy

Use conservative defaults that are easy to audit:

| Condition | Initial action | Reason |
|---|---|---|
| `odds >= 100` | block | Latest report: odds 100+ was 45 bets, ROI 0.00%. |
| `win_selection_ev >= 5` | block | Latest report: ev>=5 was 50 bets, 0 wins, ROI 0.00%. |
| `50 <= odds < 100` | require top probability rank and shrink stake | Tail may contain rare value, but should not dominate bankroll. |
| `3 <= win_selection_ev < 5` | shrink stake unless probability/rank gate passes | EV is currently odds-correlated, not result-correlated. |

### Required Diagnostic Run Metadata

Minimum fields: `backtest_run_id`, `generated_at_utc`, `git_commit`,
`train_start`, `train_end`, `test_start`, `test_end`, `test_year`,
`betting_target`, `models_dir`, `strategy_manifest_path`,
`strategy_manifest_sha256`, `feature_manifest_sha256`, `timing_mode`.

`.planning/spikes/MANIFEST.md` exists, but no packaged spike findings skill was

if those findings should become canonical.

<deferred>
## Deferred Ideas

- Month-specific betting filters based on the 2024 monthly ROI table. These are
  too likely to overfit and should not be implemented without multi-year evidence.
- Wide-odds 153-column dimensionality reduction. This may be useful, but it is
  secondary to fixing artifact consistency, true OOF, and known unhealthy columns.
- Expanding the project to a separate fully fledged 前日 model. This phase should
  add timing manifests and guardrails, not build a new model variant.
- Larger rolling-window CV expansion beyond the minimum needed to validate this
  phase's defensive rules. Useful later, but not required before Phase 37 planning.

</deferred>
