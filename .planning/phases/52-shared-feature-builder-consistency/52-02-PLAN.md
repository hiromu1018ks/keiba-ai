## Key design decision for TrainingPipeline integration

**Approach: FeatureBuilder processes all surfaces, callers filter afterward.**

The current code flow is:
1. `TrainingPipeline.run()` builds `feat_df` for ALL surfaces (FeatureEngine.build_all + distance_band + NAR filter)
2. `run()` loops over surfaces, filters `feat_df[feat_df["surface"] == surface]`, passes `subset_df` to `_train_submodel()`
3. `_train_submodel()` enriches the surface-filtered `df` with 13 feature modules + computes track_stats from the surface-filtered data

After migration:
1. `TrainingPipeline.run()` calls `FeatureBuilder.build_for_training()` ONCE, producing the full feature DataFrame with all 13 enrichment modules already applied
2. `run()` filters by surface as before, passes filtered `df` to `_train_submodel()`
3. `_train_submodel()` does NOT call FeatureBuilder at all — it only computes `track_stats`/`track_month_stats` from its surface-filtered `df` (using existing `_compute_track_stats()`/`_compute_track_month_stats()`), then proceeds directly to model training (MarketModel, Stage1, etc.)

This approach requires zero changes to FeatureBuildResult or FeatureBuilder API. `_train_submodel()` simply loses its feature construction code and becomes shorter.
